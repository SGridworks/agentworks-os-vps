    AI Agent Rule-Pack Authoring Guide¶

    Audience: an AI coding agent the operator has tasked with writing or modifying a rule pack for AgentWorks OS.

    Operator hand-off: "follow this guide to write a rule pack that does X."

    Companion doc (canonical schema reference): docs/rule-pack-authoring.md. This file is operational — what to do, in what order, with verification. The companion is the schema dictionary.

    Target version: v0.1.9.

    How to read this guide¶

    You are writing a YAML file the policy engine will load. A rule pack is the difference between an agent that might do something illegal and one that cannot. Get this wrong and either:

    • Real compliance violations slip through (the operator gets sued), or
    • Legitimate actions get blocked (the operator stops using the substrate).

    So:

    1. Always run §1 intake before drafting. Don't skip — half of failed packs are scoping failures, not YAML failures.
    2. Use the validation loop in §5 every time you touch the YAML. Hand-eyeballing rule logic does not work.
    3. Never claim attorney review yourself. Section §3 is explicit about when attorney_reviewed: true is allowed (it isn't, for you).
    4. Cite the source for every block decision. A reviewer must be able to defend the decision in writing — citation: is not optional for blocks.
    5. Stop and ask when the operator's intent is ambiguous about what should be blocked vs. routed to review. The conservative default is route_to_review — choose that if uncertain and surface the question.

    §1 — Intake¶

    Before opening an editor, get the operator to answer five questions. If you don't know all five, you will write the wrong pack.

    *"Five questions before I draft a rule pack:

    1. Pack identity. What's the pack_id (kebab-case, stable forever)? What industry and jurisdiction does it cover?

    2. Tier. Is this free (generic templates, no legal warranty), paid (SGridworks-credentialed), or attorney-reviewed (an attorney has reviewed it and signed an engagement letter)?

    3. Scope. What action kinds should it evaluate? Email? SMS? CRM writes? PDF generation? List all that apply.

    4. Decisions. For each rule, what should fire — block, route_to_review, or allow-with-citation? When in doubt, default to route_to_review.

    5. Source authority. What law, regulation, or internal policy backs each rule? I need a citation for every block. 'Because the lawyer said so' isn't enough — give me the section number or policy URL."*

    Capture the answers verbatim before continuing. If the operator says "use your judgment," push back: "I can draft something to start from, but you'll need to confirm scope and citations before this is safe to enforce. OK to proceed with placeholders for what you'll need to fill in?"

    §2 — Locate the rule-packs directory¶

    Rule packs live in rule-packs/<pack-id>/<pack-id>-v<version>.yaml in the repo, and at runtime in the daemon's RULE_PACKS_DIR (default: /app/rule-packs/ inside the container, mounted from the installed source checkout).

    ls $HOME/.agentworks/source/rule-packs/ 2>/dev/null || \
  ls ./rule-packs/ 2>/dev/null

    Verify: you see existing packs (smb-starter/, tcpa-real-estate/, fair-housing/).

    Fix: if no rule-packs directory exists, the operator either has not run the installer or is not in a source checkout. Confirm the install path before writing.

    §3 — Decision: tier and review status¶

    The tier field is a legal claim. Pick wrong and the operator can't enforce the pack truthfully.

    Tier Means Who can write it
    free Generic template. No legal warranty. Customer is on their own. Anyone, including AI agents.
    paid SGridworks-credentialed. Generated by domain experts under SG's name. Internal SG authors only. Set credentialed_by: "SGridworks".
    attorney-reviewed An identified attorney has reviewed it. Engagement letter on file. Only after attorney sign-off.

    Rule for AI agents: you write tier: free packs. You may draft paid or attorney-reviewed packs as starting points, but you set tier: free and attorney_reviewed: false and attorney_name: null in the file you ship. The operator changes those fields manually after the appropriate human review.

    Decision point: confirm tier with the operator:

    "This pack will ship as tier: free with attorney_reviewed: false. If you want a credentialed or attorney-reviewed pack, you'll need to (a) get human review and (b) edit those fields yourself before deployment. OK to proceed at free?"

    §4 — Draft the YAML¶

    Start from rule-packs/smb-starter/smb-starter-v0.1.yaml as a skeleton. Don't write from scratch — too easy to miss a required field.

    cp $HOME/.agentworks/source/rule-packs/smb-starter/smb-starter-v0.1.yaml \
   /tmp/<pack-id>-draft.yaml

    Edit the draft. Required top-level fields:

    schema_version: "awcp/v0.1"
pack_id: "<from-§1>"
pack_version: "0.1.0"
pack_name: "<human-readable>"
pack_description: |
  What this pack covers. One paragraph. Mention the jurisdiction if applicable.
tier: free
credentialed_by: null
attorney_reviewed: false
missing_data_disposition: route_to_review

rules:
  - rule_id: "<PACK>-<NUM>"
    name: "..."
    description: |
      What this rule does and why.
    required_data: ["..."]
    disposition_when_missing: route_to_review
    conditions:
      - when:
          field_name: ["value1", "value2"]
        then:
          decision: block
          reason: "..."
          citation: "47 U.S.C. § 227"

test_fixtures:
  - name: "blocks an unconsented SMS to a US number"
    input:
      kind: "sms.send"
      payload: { to: "+15551234567", body: "..." }
    expected: { decision: block, rule_id: "MY-PACK-001" }

    §4.1 Action-kind targeting¶

    The pack only evaluates actions whose kind matches an action your rules look at. If a rule's when: block references no field present in the action, the rule is silently skipped. To force the engine to consider a rule, list required_data so the engine knows which fields it expects to see.

    §4.2 Severity-aware aggregation¶

    Within a pack, decisions aggregate as block > route_to_review > allow. So if any rule blocks, the pack blocks. Order rules from most-specific to most-general; this matters less for correctness (severity beats order) but a lot for readable test failures.

    §4.3 Missing-data behavior¶

    disposition_when_missing per-rule, falling back to missing_data_disposition per-pack, falling back to route_to_review (the safe default). Do not set this to allow unless you can defend why missing data is genuinely safe. A rule that needs consentRecordRef but allows when it's missing is worse than no rule at all.

    §4.4 Citations¶

    Every decision: block MUST have a non-null citation:. Reviewer-facing reasons need a source. Patterns:

    • US Code: "47 U.S.C. § 227(b)(1)(A)(iii)"
    • CFR: "16 C.F.R. § 310.4"
    • State law: "Cal. Bus. & Prof. Code § 17529.5"
    • Internal policy: "sgridworks-internal-policy/dnc-2026"
    • Industry rule: "NAR Code of Ethics, Article 12"

    For route_to_review, citation can be null — but only if the rule is genuinely advisory.

    §5 — Validation loop¶

    Run all three checks every time you save the YAML. Hand-reading is not enough.

    §5.1 Schema validation¶

    Validate the YAML against the rule-pack schema with the policy-engine validator (offline, no daemon required):

    # From the repo checkout:
pnpm --filter @agentworks/policy-engine validate:pack -- /tmp/<pack-id>-draft.yaml

    Verify: the validator exits 0 with no schema errors. Any validation failures print the offending field path and a Zod error message.

    Fix: read the error path. The most common errors:

    Error Cause Fix
    must NOT have additional properties Typo in a field name (e.g., condition: instead of conditions:) Re-read companion doc §"Pack Structure".
    rules must NOT have fewer than 1 items Empty rules: [] Add at least one rule.
    condition.then must have required property 'reason' Forgot the user-facing reason Always include reason: for any decision.
    pack_version must match pattern … Not semver Use 1.2.3 form, not v1.2 or 1.2.
    schema_version must match pattern … Wrong AWCP version Currently "awcp/v0.1" exactly.

    §5.2 Test fixtures¶

    Every rule needs at least one test fixture that triggers it. Add to the test_fixtures: block:

    test_fixtures:
  - name: "<descriptive name>"
    input:
      kind: "<action.kind>"
      payload: { ... }
      context: { ... }
    expected:
      decision: block | allow | route_to_review
      rule_id: "<which rule should fire>"  # null if expecting allow with no fire

    Run schema validation again before the live policy check:

    # From the repo checkout:
pnpm --filter @agentworks/policy-engine validate:pack -- /tmp/<pack-id>-draft.yaml

    Verify: the validator exits 0; then use /api/policy/check with your fixture payloads for end-to-end decisions.

    Fix: if a fixture says expected: block but got route_to_review, the most common cause is missing-data disposition firing first (the action didn't include the field the rule needs). Add the field to payload: or set disposition_when_missing: <expected> on that rule.

    §5.3 Adversarial cases¶

    For every block rule, add a route_to_review or allow test fixture that's almost the same shape but should NOT trigger the block. Example:

    - name: "blocks SMS to US number without consent"
  input:
    kind: "sms.send"
    payload: { to: "+15551234567", consentRecordRef: null }
  expected: { decision: block, rule_id: "TCPA-001" }

- name: "allows SMS to US number WITH consent"
  input:
    kind: "sms.send"
    payload: { to: "+15551234567", consentRecordRef: "consent-2026-04-01-abc" }
  expected: { decision: allow }

- name: "doesn't block SMS to a UK number (out of scope)"
  input:
    kind: "sms.send"
    payload: { to: "+447700900000" }
  expected: { decision: allow }

    Without the negative cases, you'll write a rule that blocks correctly but also blocks every other action — and won't notice until production.

    §6 — Install the pack¶

    Once §5 passes:

    mkdir -p $HOME/.agentworks/source/rule-packs/<pack-id>
cp /tmp/<pack-id>-draft.yaml \
   $HOME/.agentworks/source/rule-packs/<pack-id>/<pack-id>-v0.1.yaml

    Reload packs in the running daemon (no restart required):

    curl -sS -X POST http://127.0.0.1:7710/api/policy/packs/reload | head -c 300

    Verify:

    curl -sS http://127.0.0.1:7710/api/policy/packs/stats | head -c 500

    Your pack appears with the right rulesCount.

    §7 — Shadow mode before enforce¶

    Never enable a new pack in enforce mode immediately. Run it in shadow first.

    Shadow mode (default for newly installed packs in v0.1.x) means the engine evaluates the pack and logs decisions to the audit trail, but does not actually block actions. The operator reviews the shadow decisions and confirms the pack is firing on what it should before flipping to enforce.

    curl -sS -X POST http://127.0.0.1:7710/api/policy/packs/<pack-id>/shadow \
  -H "content-type: application/json" \
  -d '{"shadow": true, "shadowDays": 7}'

    After shadow window, if everything looks right:

    curl -sS -X POST http://127.0.0.1:7710/api/policy/packs/<pack-id>/shadow \
  -H "content-type: application/json" \
  -d '{"shadow": false}'

    Tell the operator:

    "Pack <pack-id> is installed in shadow mode for 7 days. During that window every shadow decision logs to the audit trail but no action is blocked. Watch the audit log for surprises — if the pack fires on legitimate actions, fix the rule before flipping to enforce. After 7 days, run [§7's flip command] to enforce."

    §8 — Final report¶

    Post this to the operator:

    Rule pack <pack-id> drafted.

Pack identity:    <pack-id> v<version>
Tier:             free (non-attorney, no warranty — operator must upgrade if they want credentialed)
Scope:            <action kinds covered>
Rules:            <count>, all with citations for block decisions
Validation:       schema OK, all test fixtures pass (including <N> adversarial)
Install path:     rule-packs/<pack-id>/<pack-id>-v0.1.yaml
Shadow mode:      <on/off>, <N> days

Open questions for you (operator):
  1. <anything you weren't sure about during intake — ambiguous scope, missing
     citations, etc. Be specific.>
  2. <which packs this should layer with — does this conflict with smb-starter?
     test against your real fixture set before flipping to enforce.>
  3. <when do you want to flip to enforce mode — date or audit-log threshold?>

What you should do next:
  1. Re-read every rule end-to-end. If you run the Admin UI package separately,
     use its rule-pack editor; otherwise inspect the YAML directly.
  2. Watch the audit log for the shadow window. Surprise fires = bug in the rule.
  3. If this should be 'paid' or 'attorney-reviewed' tier, get that done before
     the shadow window ends. I cannot make those tier claims for you.

    Reference: common authoring mistakes¶

    Mistake Why it's wrong Right way
    Block without citation A reviewer can't defend the block Always include citation:
    disposition_when_missing: allow Lets unverified actions through Default to route_to_review
    One rule covering many decisions Hard to update; obscure failures Split into multiple rules, each one decision
    Test fixtures that all trigger blocks Doesn't test the negative path Add allow + route_to_review fixtures
    pack_id matches an existing pack Silently overwrites at load time Check /api/policy/packs/stats first
    Hard-coded jurisdiction in rule name Rule reads wrong if reused elsewhere Put jurisdiction in pack_description, keep rules portable
    YAML anchors / merge keys The validator may reject; harder to read Inline the values
    Citations as URLs only URLs rot Include the legal-section number; URL is supplemental
